## 2. Short analysis per system

### Hospital service robots

**Moxi (Diligent).** The most humanoid-like precedent in hospitals: a torso and one arm on a mobile base. Requests came from iPad kiosks around the hospital, by text message, and from EHR rules (e.g. "room marked clean → deliver admission bucket"). The ChristianaCare study (89 deliveries, 33 h of observation) is the best evidence we have on what goes wrong. The problems were **social and organisational** more than interface problems. Nobody knew whose job it was to meet the robot. It stood silently at the station or span in circles when its spot was blocked. It needed a human associate with a remote for lifts and doors. Infrequent users could not open its drawers. Proof News documented a system where nurses unplugged it. It got lost, waited at lifts and pinned a nurse in a lift. Nurses read it as a statement that "robots were worth spending money on; the nurses weren't". **Lessons:** (a) every arrival and every "I need help" must go to a *named role* with a clear call to action; (b) never "silently stuck"; (c) a remote-control fallback is normal, so design it in rather than treat it as failure; (d) position the robot as the nurses' tool, not management's replacement for them. (d) is a deployment message, and the UI supports it with an "on behalf of" request model and nurse-owned controls.

**TUG (Aethon).** The classic "pick destinations → Go" touchscreen. Mutlu & Forlizzi's 15-month ethnography found the *same robot* rejected on a busy medical ward and accepted on post-partum. The deciding factors were **tolerance for interruptions**, perceived cost vs. benefit, and clutter. The theatre is the least interruption-tolerant place in the hospital, so the G1 must need attention less often than any delivery robot. Separately, the 2022 "JekyllBot:5" vulnerabilities in the TUG fleet server show that the robot's web server is a hospital attack surface.

**Relay, Pudu, Keenon, Ottonomy.** Convergent pattern: a large tile grid of destinations, PIN or badge to open compartments, a chain-of-custody log, lift/door integration and nurse-station requests. In Singapore, SGH's "Swiftie" AMRs already carry sterile surgical instruments between buildings. Sengkang General deployed 37 MiR250s (2024–25), Woodlands Health Campus runs 20 Aethon robots, and TTSH uses AMRs for scopes and medication. **Theatre staff in Singapore may already know AMR delivery conventions**, and the G1 app should feel familiar to them: tiles, PIN, "arrived" notifications. Robot–lift–door integration is standardised locally as **SS 713:2025** (replaces TR 93).

### Robot operator apps

**Spot tablet app.** The closest analogue for a *legged* robot. Worth copying:
- **Lease / control ownership.** Only one client controls the robot; others can watch, and control is taken explicitly.
- **Comms watchdog.** 3 s without the controller → sit; 8 s → motors off.
- **Status bar** always visible: battery, comms, motor power.
- **Autowalk** record → replay, with the rule that the operator stays connected and supervises. Boston Dynamics restricts Autowalk to "after-hours, away from people", which tells us how conservative a humanoid in a theatre must be.
- **Stop semantics.** STOP cuts motor power and the robot collapses, and the manual says not to use it on stairs where collapsing is worse.

The G1 has the same problem in a sharper form: DAMP makes the G1 "slowly fall to the ground" (Unitree docs), next to a patient and a sterile field. Agility's Digit 5 answers it with a **Category 1 controlled stop**, a safety PLC and the ability to **sit down and power off** when people approach. ISO 25785-1 (draft, dynamically stable robots) exists because cutting power is not a safe state for these machines. → See `02` rule S-1: the iPad must offer a *hold* stop and treat DAMP as a last resort.

**Seirios RNS (Movel AI).** The user's reference and the existing G1 Console's inspiration. It gets these right: a map-centric dashboard, a mode-dependent button set, a Task Manager (tasklist + scheduler with Run now / Add to queue), a "Health Care" error log, light/dark mode, and Owner/Admin/Staff roles. Its own documentation warns that *E-stop disconnects motor power* and that users should use *Clear tasks* to abort. So the vendor already knows users confuse "stop the job" with "stop the robot". Our app must make those two different buttons with different words.

**BrainOS (Brain Corp).** The best evidence that non-technical staff can *teach* robots. Teach-and-repeat means driving the route once and replaying it. Its touchscreen has three jobs (teach a route, run a route, watch training videos), and its "glanceable UI with international symbols" works across languages. This is the model for the "Teach a new task" feature.

**MiR / OTTO / Orbit / Agility Arc.** Fleet tools: PIN login, user groups with per-feature permissions, tailored dashboards, map-centric job queues, KPIs such as uptime and Mean Time Between Incidents. Forum feedback on MiR ("pretty but not designed for usability") is a reminder that visual polish without task focus fails. **Map editing, scheduling and fleet KPIs belong on a desktop/manager view, not the bedside iPad.**

**Unitree Explore.** The vendor app provides joint temperatures, calibration and "Training Mode" (pose by hand, record). In a hospital it is a liability. The G1's BLE provisioning uses a hard-coded shared AES key (UniPwn, Sept 2025, wormable between robots), and researchers observed telemetry to vendor servers every 5 minutes. Our app replaces it for daily use, and the technician view must show that the vendor cloud path is blocked.

**Figure / Tesla / Apptronik.** No public operator UIs. Their training pipelines (teleop, VR, camera rigs; "only successful trials are kept") confirm that a "teach" flow needs **demonstration curation**, not just recording.

### Surgical robots

All four surgical platforms separate **the surgeon's glance surface** from **the team's control surface**. da Vinci 5 has a head-in menu and a universal UI across console, tower and cart. Hugo has a surgeon display plus an OR-team tower touchscreen. Versius has an open console and visible arm state. Mako puts state on the tool itself (tool icon colour, voxel colours) and runs a strict step workflow. Ottava is designed to be "invisible when not needed". For us:

1. The surgeon never operates the iPad. The surgeon talks (to the circulator now, to the robot later) and glances at the robot and the room display.
2. The robot's **own body** (head/chest light, arm pose, speech) is the primary state display for people in the sterile field; the iPad is the team's control surface.
3. Missions are shown as **steps** (Mako-style), with the current step highlighted and the next step previewed.
4. Mako's green/red voxels show a colour-vision hazard we must avoid (see `05`).

### Clinical apps

**Epic Rover**: a device you carry and trust gets used, with 26 minutes earlier documentation and +74% barcode adherence after individual devices at the Royal Children's Hospital, Melbourne. For utilisation, the iPad must be *always charged, always on the right screen, instantly unlocked by badge/PIN*, not "the tablet in the drawer".
**Vocera**: hands-free lowers friction but *increases felt interruptions*. The robot's notifications need a budget.
**OR boards / e-checklists**: a shared 40" checklist lifted patient-ID confirmation from 51% to 99% (Vanderbilt), and flight boards improved all 10 surgeons' compliance. Shared visible state works. The robot should *participate* in the WHO time-out ("robot present, instrument rack verified, stop control assigned to: circulator") rather than add a separate ritual.

## 3. Patterns to adopt

| Pattern | Seen in | How we use it |
|---|---|---|
| "Pick a place → Go" tiles | TUG, Pudu, Relay | Clinical Home: *Send to…* grid of named rooms (Theatre 1, Sterile store, Scrub, PACU, Dock) |
| Mode-dependent action set | Seirios, Spot | The action panel shows only the legal next actions for the current mode (from `hello.transitions`) |
| Lease / single controller + observers | Spot SDK | One iPad holds "control"; others are observers; explicit "Take control" with reason, logged |
| Comms watchdog | Spot | Manual modes drop to STAND (hold) if the controlling iPad goes silent for > 1 s; nav/auto continue but alert |
| Record → replay under supervision | Spot Autowalk, BrainOS | "Teach a new task" (upcoming) |
| Step workflow with current step | Mako | Mission view as a vertical stepper |
| State on the machine | Mako, Versius | Robot status light + spoken phrases mirror the app's mode colour |
| Split audiences | Hugo, da Vinci 5 | Clinical mode (team) vs Across-room glance view (surgeon) vs Technician |
| Role dashboards + PIN | MiR, Seirios | Clinical / Operator / Technician modes behind PIN or badge |
| Audit trail | Relay | Every command logged with user, role, device, source |
| Shared confirmation | OR checklists | Robot readiness is a time-out line item |
| Built-in training videos | BrainOS | "How do I…" 30-second clips per flow, offline |

## 4. Patterns to avoid

| Anti-pattern | Seen in | Instead |
|---|---|---|
| Silent robot when stuck or arrived | Moxi | Escalating, targeted notice: robot speaks, app shows a named call to action, then medium alarm after N s |
| One "E-stop" that means both "abort task" and "kill power" | Seirios (documented) | **Stop** (hold still, keep balance) vs **Emergency power-off** (DAMP, robot sinks) as separate, labelled controls; hardware e-stop is the real e-stop |
| Confirm dialog on STOP | Spot tablet STOP | Stop is one tap, no confirmation; *resume* needs the confirmation |
| Red/green-only state | Mako voxels, many checklists | Colour + icon + word, CVD-safe palette |
| Engineer UI in clinical hands | Current G1 Console (topic names, `policy hz`, `placeholder: yes`) | Technician-only; Clinical shows plain-language state |
| Vendor cloud dependency | Unitree app | Local-only, hospital-controlled network |
| Tablet in a drawer, flat battery, wrong login | Shared-device studies | Docked, charged, kiosk-locked, badge/PIN quick switch |
| More notifications = more help | Vocera | Interrupt budget: at most one audible robot message per few minutes in theatre, except safety alarms |
